`[outputs.<section>]` is the **app → hardware** direction of a mapping: it watches a closed-catalog signal for the section and emits MIDI when it turns on or off — how the app lights LEDs and drives callbacks on the controller. This page is the reference for the table; [map.toml](/docs/developers/midi-mappings/map-toml) is its overview, [inputs](/docs/developers/midi-mappings/map-toml/inputs) is the opposite (hardware → app) direction, and the control declarations these targets point at live in [device.toml](/docs/developers/midi-mappings/device-toml).

Sections are `deck_1` through `deck_4`, `master`, `sampler`, and `custom`. Only `deck_*` sections resolve signals, and `master` resolves `master_cue` and `fx_armed`; `sampler` and `custom` are host-driven only.

## Binding fields

Every output binding accepts these fields:

| Field | Required | Default | Notes |
| --- | --- | --- | --- |
| `signal` | no | — | Closed-catalog signal name driving the LED. Absent → host-driven via `apply_output_signal`. |
| `on` | yes | — | Target sent when the signal turns true. Alias or inline endpoint. |
| `off` | yes | — | Target sent when the signal turns false. Alias or inline endpoint. |
| `blink` | no | — | Third-state target: while the signal is true the LED alternates `blink`/`off`. Requires `signal`. |

```toml
[outputs.deck_1]
play_pause = { signal = "playing", on = "play_led", off = { type = "note", channel = 1, note = 0x0B, velocity = 0x00 } }
```

## Targets: aliases vs inline

Each of `on`, `off`, and `blink` is one of:

- an **alias** resolved against `device.toml` — a section-local bare name, a `section.alias` reference, or a bare name searched across sections;
- an **inline endpoint** table (`type`, `channel`, and the fields its type requires) serialized directly.

Alias targets resolve exactly like input aliases, so an unresolvable name fails with `outputs.<section>.<alias>.on: alias '<name>' missing from device.toml`.

## Signal catalog

Signals are a closed catalog per section: a name outside the list fails load with `unknown signal 'x' for 'deck_1'`.

### Deck signals

| Signal | Meaning |
| --- | --- |
| `playing` | Deck playhead running. |
| `cue_hold` | Cue held. |
| `sync` | Deck is sync master. |
| `quantize` | Quantize on. |
| `headphone_cue` | Headphone cue (PFL) on. |
| `track_loaded` | Track loaded in the deck. |
| `loop_active` | Loop engaged. |
| `loop_in_set` | Loop-in point set. |
| `shift_held` | A `custom.<alias>` modifier for the section is held. Resolved from the session modifier set, not the engine snapshot. |
| `pad_mode_hot_cue` | Deck pad mode is Hot Cue. |
| `pad_mode_loop_roll` | Deck pad mode is Loop Roll. |
| `pad_mode_beat_jump` | Deck pad mode is Beat Jump. |
| `pad_mode_sampler` | Deck pad mode is Sampler. |
| `pad_mode_stems` | Deck pad mode is Stems. |
| `pad_mode_keyboard` | Deck pad mode is Keyboard. |
| `pad_mode_key_shift` | Deck pad mode is Key Shift. |

### Slot signals

| Pattern | Range | Meaning |
| --- | --- | --- |
| `hot_cue_<n>` | `n` = 1..=16 | Library hot-cue slot n holds a cue. |
| `loop_slot_<n>` | `n` = 1..=8 | Saved-loop slot n is populated. |
| `pad_hot_cue_<n>` | `n` = 1..=8 | Mode-gated: slot n has a cue, only on the Hot Cue page. |
| `pad_loop_<n>` | `n` = 1..=8 | Mode-gated: slot n is backed by a saved loop, only on the Loop Roll page. |
| `pad_beat_jump_<n>`, `pad_sampler_<n>`, `pad_stems_<n>` | `n` = 1..=8 | Mode-gated, but always resolve false — there is no engine slot LED state for these pages yet. Bind them anyway so attach forces the bank off. |

Because a pad bank is mode-gated, only the deck's active page can light; the previous page's bank goes dark as soon as the mode changes. `pad_keyboard_*` / `pad_key_shift_*` are deliberately not advertised — those banks are host-driven (see [Host-driven outputs](#host-driven-signal-less-outputs) below).

### Master signals

| Signal | Meaning |
| --- | --- |
| `master_cue` | Mixer master cue (PFL) on. |
| `fx_armed` | The shared Beat FX unit is armed (`SlotEnabled` on slot 0). |

## LED modes

Each binding resolves to one of three states:

| State | Condition | Wire effect |
| --- | --- | --- |
| `Off` | Signal false | Sends `off`. |
| `On` | Signal true, no `blink` declared | Sends `on`. |
| `Blink` | Signal true and `blink` declared | Alternates `blink` and `off` every 200 ms (≈2.5 Hz full cycle). The lit phase uses `blink`, never `on`. |

The session advances the blink phase from the MIDI pump (`tick_leds`); a bundle whose outputs declare no `blink` anywhere skips the scan entirely.

The DDJ-400 uses blink for the +SHIFT mode indicators: while `shift_held` is true the lamp flashes instead of sitting solid.

```toml
pad_mode_loop_roll_shift = { signal = "shift_held", blink = "pad_mode_loop_roll_shift_led", on = "pad_mode_loop_roll_shift_led", off = { type = "note", channel = 1, note = 0x1E, velocity = 0x00 } }
```

<Callout type="warning" title="Don't blink a shared address">
In the DDJ-400, notes `0x69`/`0x6F` belong to the Keyboard / Key Shift mode lamps — the same physical LEDs as SHIFT+HOT CUE / SHIFT+SAMPLER. Blinking `shift_held` on those addresses fights the solid mode `On` and flickers. One output per physical LED.
</Callout>

## Caching and refresh

- The last state per binding is cached as `section.alias`, so the same state is never re-sent: an `on` is followed by an `off`, not by repeated `on` messages.
- State is deliberately **forced** to re-send after a pad-mode switch (`set_deck_pad_mode` → `refresh_deck_leds`), since hardware often clears pad LEDs when the page changes: the session drops the cached value and replays the hot-cue LED state.
- On attach, the `[lifecycle]` `on_init` script runs first, then a forced sweep (`refresh_all_leds`) re-asserts every lamp — the unit may still hold state from a previous run.
- On shutdown and detach, every mapped lamp's `off` bytes are sent (`clear_leds`); the cache is dropped first so a failure mid-sweep cannot leave a stale lit entry.
- Continuous-value commands (jog, EQ, volume, …) skip the per-deck LED resolve on purpose.

## Host-driven (signal-less) outputs

Without `signal`, the binding key doubles as the watch name and must be a closed input alias for that section — except in `custom`, where any snake_case key is allowed. The host lights these via `apply_output_signal`.

The DDJ-400's Keyboard and Key Shift pad banks are signal-less for exactly this reason:

```toml
keyboard_pad_1 = { on = "keyboard_pad_1_led", off = { type = "note", channel = 8, note = 0x40, velocity = 0x00 } }
```

The host re-drives them whenever the deck enters a keyboard or key-shift page (`refresh_key_shift_leds`), following the key-shift state, the keyboard page, and the root cue. These are host-owned lamps, unlike the declarative signals above: `[lifecycle]` scripts cannot read or write them.

VU meters are not `[outputs]` bindings. The host drives the `vu_meter` endpoint declared in `device.toml` (`set_deck_vu`), sending CC value `level × 150` clamped to 127 (the Mixxx scale) and skipping duplicate values.

## DDJ-400 worked examples

| Control | Signal | On target | Off target |
| --- | --- | --- | --- |
| Play/pause lamp | `playing` | alias `play_led` | inline note ch 1 `0x0B` |
| Loop group (`loop_out`, `loop_out_shift`, `exit_loop`, `exit_loop_shift`) | `loop_active` | per-lamp aliases | inline notes ch 1 `0x11`/`0x4E`/`0x4D`/`0x50` |
| Hot-cue pad bank (deck 1) | `pad_hot_cue_1` … `pad_hot_cue_8` | alias `hot_cue_pad_led1..8` | inline notes ch 9 `0x00`..`0x07` |
| Master cue | `master_cue` | alias `master_cue_led` | inline note ch 7 `0x63` |
| Beat FX ON/OFF (`beat_fx_on`, `beat_fx_on_shift`) | `fx_armed` | aliases `beat_fx_on_led` / `beat_fx_shift_led` | inline notes ch 5 `0x47` / `0x43` |
| +SHIFT mode indicators | `shift_held` | alias (also `blink`) | inline notes ch 1 `0x1E`/`0x6B` |

## Validation errors

| Error | Fix |
| --- | --- |
| `unknown outputs section 'x'` | Use `deck_1`..`deck_4`, `master`, `sampler`, or `custom`. |
| `outputs.<section>.<alias>: alias must be snake_case` | Rename the binding key. |
| `outputs.<section>.<alias>: watch key not in closed catalog` | A signal-less binding key must be a closed input alias for that section (any snake_case key works in `custom`), or add a `signal`. |
| `outputs.<section>.<alias>: 'blink' requires 'signal' (otherwise the binding is never resolved)` | Add `signal = "…"` — without one the binding is only host-driven and can never blink. |
| `outputs.<section>.<alias>: unknown signal 'x' for 'deck_1'` | Use a signal from this page's catalog for that section. |
| `outputs.<section>.<alias>.on: alias '<name>' missing from device.toml` | Declare the alias in `device.toml`, or switch to an inline endpoint. |
