`library.db` is the source of truth for track information. Write-back is the optional second half: when the user turns on **Settings → Library → File tags**, Mixar also writes values into each file's own tags so other software (Rekordbox, Serato, Traktor, Mixxx, Mixed In Key) sees the same ones.

It is the only place Mixar modifies a music file, so it is opt-in, field-scoped, idempotent, and best-effort.

User-facing manual: [Tag write-back](/docs/users/library/tag-write-back) (in [Library](/docs/users/library)). This page covers internals, the field matrix, and the known limits.

- Opt-in: `LibraryConfig::tag_write_back` (`Off` by default; `TagWriteBack::On` from the setting). With it off, no analysis path ever opens a file for writing.
- Field-scoped: `TrackTags` is a patch, not a rewrite. Only the fields the caller sets are touched; pictures, ReplayGain, Serato frames, and foreign keys survive untouched. A blank string or a non-finite BPM is reported `Absent` and written nowhere.
- Idempotent: a field already carrying the wanted value is left alone, and a file with nothing to change is never rewritten (no mtime churn, no re-padding on every analyze).
- Best-effort: an unwritable file is logged and skipped; the library row is already committed.

Implementation: `codec::write_track_tags` (lofty) for the format matrix, called by `library::tags::write_back_track_tags` from `LibraryManager::persist_file_analysis` and the `SaveBeatGrid` worker handler. Neither runs on the audio callback; the beat-grid path plans the write while holding the library lock and performs the file I/O after releasing it.

## Fields per container

|           | ID3v2 (mp3/wav/aiff/aac) | Vorbis comments (flac/ogg/opus) | MP4 `ilst` (m4a)                    | APE (ape/wv/mpc) |
|-----------|--------------------------|---------------------------------|-------------------------------------|------------------|
| Title     | `TIT2`                   | `TITLE`                         | `©nam`                              | `Title`          |
| Artist    | `TPE1`                   | `ARTIST`                        | `©ART`                              | `Artist`         |
| Album     | `TALB`                   | `ALBUM`                         | `©alb`                              | `Album`          |
| Genre     | `TCON`                   | `GENRE`                         | `©gen`                              | `Genre`          |
| BPM       | `TBPM`, **integer**      | `BPM`, text                     | `----:com.apple.iTunes:BPM`, text   | unsupported      |
| Key       | `TKEY`                   | `INITIALKEY`                    | `----:com.apple.iTunes:initialkey`  | unsupported      |
| Rating    | `POPM` per email¹        | `RATING`, 0.0–1.0               | `rate`, 1–5                         | unsupported²     |
| Comment   | `COMM`                   | `COMMENT`                       | `©cmt`                              | `Comment`        |
| Year      | `TDRC`                   | `YEAR`                          | `©day`                              | `Year`           |
| Track no. | `TRCK`                   | `TRACKNUMBER`                   | `trkn`                              | `Track`          |
| Disc no.  | `TPOS`                   | `DISCNUMBER`                    | `disk`                              | `Disc`           |
| Color     | `COLOR`                  | `COLOR`                         | `----:com.apple.iTunes:COLOR`       | `Color`          |

¹ ID3v2 keeps the rating in a binary `POPM` frame keyed by the email of the app
that wrote it. Multiple frames are legal, so Mixar writes one per writer:
MusicBrainz Picard's frame goes through lofty's provider
(`round(star * 51)` — `51/102/153/204/255`), and Traktor, MusicBee and Windows
Media Player get the stepped `1/64/128/196/255` set. Each app reads the frame
carrying its own email, so the same star count reaches all of them at once. A
frame owned by a reader Mixar does not mirror is re-emitted on the stepped set:
a stepped writer (Serato, MediaMonkey, foobar2000) keeps its exact byte, while a
51-scale one keeps its star. Each mirrored frame keeps its play counter.

² APE has no rating key in lofty's (or TagLib's) mapping table, so the field is
reported `Unsupported` on `.ape`/`.wv`/`.mpc`.

MP4's `rate` atom keeps the scale Mixar has always written: the star count
itself (`4`). Serato 4 writes a `RATE`/`rate` value whose scale has not been
verified against a real file, so the writer is unchanged and the reader accepts
both conventions (a value of `1–5` is the star count, `20–100` is treated as a
percentage). A literal uppercase `RATE` atom is not read: only `rate` is in
lofty's atom map, and no fixture has shown `RATE` in the wild.

A per-app Vorbis rating (`RATING:<email>=N`, which Picard writes) cannot be
written back through lofty's generic tag: its writer would put lofty's internal
`email|stars|counter` text under plain `RATING`. Any save that rewrites the file
therefore folds such an alias into the plain normalized `RATING` (`0.8` = four
stars) instead, keeping the star count every reader understands at the cost of
the per-app key.

Reading is deliberately wider than writing. Vorbis `RATING` stays raw text, so it
accepts normalized `0.0–1.0` (Quod Libet/Picard), stars `1–5`, a 0–100 scale, or
a raw POPM byte above 100 (`204` = four stars; `6–19` fit no scale and are
rejected). `POPM` frames and MP4 `rate` go through lofty's rating
providers: a known email is read on its own scale and every other email
(including an empty one) on the linear 51 scale, whose thresholds also land on
the right star for the stepped `1/64/128/196/255` writers. Two edges are
inherent: lofty's `StarRating` has no "unrated" value, so a stored `0` reads as
one star; and several mirrored frames that disagree resolve in a fixed order,
with Traktor's frame first.

The mapping matches the TagLib property table, so the keys are the ones MusicBrainz Picard, Mixxx, and the DJ tools above already read and write. Mixxx writes the same Vorbis `BPM` + `INITIALKEY` pair and the same two MP4 freeform atoms.

**What the library mirrors today is BPM, key, rating, comment, year, track/disc
number and colour label**: `library::tags::app_managed_tags` is the one place
that decides it. Title/artist/album/genre are file-derived today (a missing title
falls back to the file name), so passing the library row would stamp filename
guesses into untagged files. A track editor that owns those values extends that
one function; the writer already handles them. Derived fields (duration, sample
rate, channels, bitrate) are never written: they describe the audio, not user
intent.

## Lossiness

- **ID3v2 `TBPM` is an integer frame**, so a fractional BPM is rounded (`FieldWrite::Rounded`). Mixxx and Mixed In Key round too. `library.db` keeps the exact value, so a rescan that prefers the tag can land up to 0.5 BPM away from the stored beat grid.
- **MP4 gets the freeform `BPM` atom, not `tmpo`.** The freeform field is what Mixed In Key, Serato, and Traktor write and what Mixxx reads first; `tmpo` is an integer atom, which lofty cannot emit from a text tag. Readers that look only at `tmpo` will not see Mixar's BPM.
- **APE tags have no BPM/key mapping** in the TagLib/lofty table, so those two fields are reported `Unsupported` on `.ape`, `.wv`, and `.mpc` (the text fields work).
- **Refused shape** (`FieldWrite::Refused`, file left byte-identical): native `.stem.mp4` containers, multi-track MP4s whose `stem` manifest Mixar does not own.
- **Legacy aliases are not updated.** Only the recommended keys in the table above are written. A Vorbis file that carries the older `KEY` (or `TEMPO`) alias keeps its stale value, and the same goes for MP4's `----:com.apple.iTunes:KEY`; a reader that prefers the alias over `INITIALKEY`/`BPM` will see the old number. Mixxx additionally updates `KEY` when it is present. Aliases in the wild: Vorbis key `INITIALKEY` (Rekordbox, Serato, Traktor, Mixxx) vs `KEY` (VirtualDJ, Denon Engine DJ); Vorbis BPM `BPM` (MusicBrainz) vs `TEMPO` (Mixxx ≤ 2.0); MP4 key `----:com.apple.iTunes:initialkey` vs `----:com.apple.iTunes:KEY` (Rapid Evolution); MP4 BPM `----:com.apple.iTunes:BPM` vs the integer `tmpo` atom. Mixar *reads* either key alias, but has no mapping for the older Vorbis `TEMPO`, so a file whose BPM lives only there reads as unknown and is re-analyzed.
- **Clearing a tag is not expressible yet**: `TrackTags` uses `None` for "leave alone", so removing a field needs that added to the patch type first.

## Cues, loops, and beat grids

Cues, loops, and grids are not written to tags: there is no *standardized* tag representation. Serato's proprietary, reverse-engineered field set is the de-facto one, and it is per-format: ID3v2.4 GEOB frames on MP3/AIFF, `SERATO_MARKERS_V2` Vorbis comments on FLAC, `----:com.serato.dj:markersv2` atoms on MP4/M4A, its own layout on Ogg Vorbis, sidecar XML for AAC. Mixxx preserves it (it re-emits the frames it parsed, never authors cues). Mixar keeps cues/loops/grids in `library.db`, as Rekordbox and Traktor do; Rekordbox's route out of the database is USB export (ANLZ files), tracked in [#452](https://github.com/geovannimp/mixar/issues/452); writing Serato's frames is tracked in [#548](https://github.com/geovannimp/mixar/issues/548).

## Verifying a change

- `cargo test -p codec tag_write`: the per-container matrix (text fields, BPM rounding, APE's missing BPM/key), the `POPM` frame per writer with its byte scale, foreign-frame reads, ID3v2/Vorbis/MP4 round trips, idempotency, and the Stem refusal.
- `cargo test -p library --all-features write`: analysis and beat-grid write-back against a real WAV, plus the untouched-file case with the setting off.
- `cargo test -p host_flutter --test library_tag_write_back`: the whole stack, app setting → `LibraryTransport` → worker analysis → file tags, read back with lofty rather than Mixar's own reader.
